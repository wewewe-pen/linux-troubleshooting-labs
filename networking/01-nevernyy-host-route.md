# Инцидент: неверный host route к `1.1.1.1`

## Симптом

`ping 1.1.1.1` не работал, хотя interface имел нормальный адрес `192.168.254.129/24`, а в таблице был обычный default route через `192.168.254.2`.

## Что проверил

Начал с базовых вещей:

```bash
ip -br addr
ip route
```

В routing table обнаружился отдельный маршрут:

```text
1.1.1.1 via 192.168.254.253 dev ens33
```

Сначала я решил, что всё равно будет использован default route. Это была первая неверная гипотеза.

`1.1.1.1` здесь фактически имел host route `/32`, поэтому по Longest Prefix Match он выигрывал у default `/0`.

Дальше проверил neighbour table:

```bash
ip neigh
```

Для `192.168.254.253` было состояние:

```text
FAILED
```

Чтобы убедиться, что kernel действительно пытается идти через этот next hop, снял capture:

```bash
sudo tcpdump -i ens33 -n 'arp or icmp'
```

Были ARP Requests к `192.168.254.253`, но не было ни одного ARP Reply.

При исправлении сначала попытался удалить:

```bash
sudo ip route del 192.168.254.253/32
```

Но `.253` был gateway, а не destination route.

## Причина

Более специфичный `/32` route отправлял трафик к `1.1.1.1` через недоступный next hop `192.168.254.253`. MAC next hop получить не удавалось.

## Исправление

Удалил именно route к `1.1.1.1/32`. После этого kernel снова начал использовать default route через `192.168.254.2`.

Проверка:

```bash
ip route get 1.1.1.1
ping -c 3 1.1.1.1
```

Результат: `3 transmitted, 3 received, 0% packet loss`.
