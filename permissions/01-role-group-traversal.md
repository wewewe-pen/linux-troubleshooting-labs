# Инцидент: доступ к application tree через роли, а не отдельных users

## Задача

Несколько accounts должны были работать с общими ресурсами приложения, при этом outsider не должен был проходить внутрь дерева.

## Первая неудачная модель

Использовалась схема, где owner был одним конкретным user, а group — другим конкретным user. Формально отдельный файл можно было заставить работать, но такая модель плохо масштабируется и смешивает account с ролью.

## Решение

Для dev/web была создана общая application group (`plabapp` / позже `p2team`).

Корень application tree строился так, чтобы:

```text
root   → администрирует
group  → рабочие accounts могут traverse
others → доступа нет
```

Для auditor использовался отдельный ACL, когда ему требовался доступ к конкретному report без добавления в общую application group.

## Что оказалось важным

Правильных permissions конечного файла недостаточно. Для доступа к нему user должен иметь `x`/traverse на всех parent directories пути.

## Вывод

- доступ удобнее проектировать через роли/groups;
- проверять нужно весь pathname, а не только конечный файл;
- blanket fixes вроде `chmod -R` легко ломают уже корректные объекты.
